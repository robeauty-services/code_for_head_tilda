# code_for_head_tilda

Скрипти, що вставляються в `<head>` сторінок Тільди: пікселі, збереження кошика,
список відвіданих сторінок.

Два сайти, два незалежні бандли з одного репо:

| Сайт | Джерело | Бандл | Інлайн-частина в `<head>` |
| --- | --- | --- | --- |
| robeauty.me (Tilda 2095616) | `src/head.js` | `dist/head.min.js` | `tilda_head_without_scripts/tilda_head.html` |
| maneraparfum.com (Tilda 9787525) | `src/manera-head.js` | `dist/manera.min.js` | `tilda_head_without_scripts/manera_head.html` |

Номери секцій у двох джерельних файлах збігаються (3 — FB, 4 — TikTok,
5 — кошик, 7 — посилання на товари), щоб їх можна було діфати між собою.

## Покупка рахується лише після оплати (robeauty, секція 9)

Тільда оголошує покупку в момент відправки форми кошика — ще до переходу на
сторінку оплати. GTM робить із цього `purchase` у GA4 і конверсії Google Ads,
тож кожна кинута чи відхилена онлайн-оплата рахувалась як продаж: у вересні 2026
за 22% покупок у GA4 не стояло жодного замовлення.

Секція 9 для замовлень з онлайн-оплатою притримує це оголошення і повторює його
без змін, коли бекенд підтвердив, що оплачене замовлення дійшло
(`GET /api/tilda-orders/order-status` у `robeauty-api`). Meta Purchase у секції 3
чекає того самого підтвердження. Замовлення з оплатою при отриманні не
зачіпаються.

- На сторінці `thanks` перевірка повторюється 5 хвилин; на будь-якій іншій —
  один раз за завантаження, протягом доби після замовлення.
- Усе відмовляє «у відкритий бік»: якщо притримати не вдалося або бекенд
  недосяжний, подія йде так, як ішла раніше.
- У GTM нічого не змінювалось. Через це `order_type` у GA4 для онлайн-оплат
  тепер `thank_you_upsell` (змінна GTM дивиться на URL сторінки) — виправляється
  однією змінною в GTM, якщо цей параметр комусь знадобиться.

## TikTok (robeauty, секція 4)

Усі події TikTok (піксель `CVSFT93C77UF96PLUHKG`) ідуть із секції 4, а
викликає її секція 3 — у тому самому місці, де йде відповідна подія Meta, з тим
самим `event_id`. Тому Purchase підпорядкований перевірці оплати із секції 9:
накладений платіж — на сторінці thanks, онлайн — лише після підтвердженої
оплати.

| Подія | Коли | Серверна копія |
| --- | --- | --- |
| ViewContent | сторінка товару | ні |
| AddToCart | додавання в кошик | так |
| InitiateCheckout | перший фокус у формі кошика | так |
| Purchase | як Meta Purchase | так |

- Серверна копія йде через PHP-релей на VPS
  (`/var/www/webhooks/tiktok_capi/tt_capi.php`, у ньому токен Events API), логи
  поруч у `logs/capi_log_<дата>.txt`. TikTok склеює дві копії за `event_id`.
- До жовтня 2026 Purchase слав блок T123 `rec1285753511` на самій Тільді — у
  момент відправки кошика, за кожне замовлення, оплачене чи ні. Його треба
  видалити, коли цей бандл на сайті. Тег GTM «ATC_TT» сам пропускає подію, коли
  на сторінці є `window.rbTikTok`.
- `fb_capi_service` має провайдер `tt`, але він ніколи не працював і зараз не
  потрібен.

## Manera: хто шле Meta Purchase (секція 5)

У піксель Manera (1010062401474550) кожну покупку має слати рівно один
відправник, і залежить він від способу оплати:

| Оплата | Хто шле Purchase |
| --- | --- |
| При отриманні (`cash`) або спосіб оплати не визначився | секція 5: піксель + серверна копія через `manera-analytics`, спільний `event_id` |
| Онлайн (WayForPay), поки `TILDA_PURCHASE_MODE` у `manera-analytics` — `off` (умовчання) або `shadow` | вбудований приймач Тільди «FB pixel»: одна подія на оплачене замовлення, але з номером HTML-блоку замість номера товару, тож каталог Meta її не впізнає |
| Онлайн, коли `TILDA_PURCHASE_MODE=live` | `manera-analytics` за вебхуком Тільди про оплачене замовлення (його пересилає `tilda-orders` з `robeauty-api`), з номерами каталогу |

Чому секція 5 не шле Purchase за онлайн-оплату: оформлення ще не оплата, а
приймач Тільди шле свою подію без `event_id`, тож Meta не склеювала її з нашою і
рахувала покупку двічі, а наша до того ж ішла і за неоплачені замовлення
(2 жовтня 2026: 164 покупки в Ads Manager проти 78 замовлень у CRM).

- **Перевірку `paymentSystem` у секції 5 не прибирати ніколи** — і тоді, коли
  приймач Тільди вимкнуть. Без неї браузер знову шле Purchase пікселем і через
  CAPI за кожне онлайн-оформлення, зокрема неоплачене, а `checkout_context`
  (він стоїть усередині тієї ж перевірки) перестає йти — і серверний Purchase
  лишається без fbp/fbc.
- Для онлайн-оплати секція 5 шле на сервер лише `checkout_context` (fbp/fbc,
  браузер і контакти з форми). У Meta ця подія не йде: `manera-analytics` тримає
  її 7 діб і прикладає до Purchase за вебхуком. Вона йде за будь-якого режиму
  сервера, перемикати тут нічого не треба.
- Перемикання онлайн-покупок на сервер — дві дії в одну хвилину:
  `TILDA_PURCHASE_MODE=live` у `manera-analytics` і вимкнений приймач «FB pixel»
  у налаштуваннях Тільди. Обидва ввімкнені — покупка рахується двічі, обидва
  вимкнені — онлайн-покупки зникають із Meta. Відкат — так само обидві разом.
- У режимі `shadow` сервер у Meta нічого не шле, а пише зібрану подію рядком у
  `logs/providers/fb/purchase_online/shadow-<дата>.log` — щоб до перемикання
  звірити номери товарів і частку замовлень, до яких знайшовся `checkout_context`.
- Ознака, що онлайн-покупки доходять: до перемикання — в Events Manager Purchase
  від приймача Тільди за годину стільки ж, скільки оплачених онлайн замовлень у
  CRM; після — стільки ж рядків у `success-<дата>.log` у
  `logs/providers/fb/purchase_online/` на сервері `manera-analytics`.

## Manera: номер товару для Meta (секція 3)

Сторінки ароматів продають кнопками `#order:Назва [sku:…]=ціна`, тож номер
товару для ViewContent / AddToCart / Purchase береться з `[sku:…]` у назві й
через `map_content_ids` міняється на номер групи товару в каталозі Meta MANERA
(`984136947662413`). SKU буває з великими літерами (`KU-0003397` — 30 мл).

- Новий товар на сайті — додати його SKU у `map_content_ids` тут, у
  `src/utils/tildaMapper.util.js` репо `manera-analytics` (серверна копія
  Purchase наложки і Purchase онлайн-оплати за вебхуком беруть номер звідти) і
  в `getContentIds` TikTok-блоку у футері Тільди. Інакше подія піде без номера
  товару.
- Значення — той самий номер, що `item_group_id` товару в каталозі.

## Що лишається інлайном у `<head>` і чому

Не все можна винести в бандл:

- `<meta name="facebook-domain-verification">` — має бути справжнім тегом у HTML.
- `<noscript>` з піксельною картинкою — за визначенням не працює через JS.
- **Growthbook** (тільки robeauty) — `trackingCallback` мусить існувати до того,
  як відпрацює auto-бандл, а сам бандл читає `data-client-key` зі свого ж
  тега `<script>`. Зовнішній файл не дає ні першого, ні другого.
- Clarity (тільки manera) — лишили інлайном, щоб запис сесії стартував не
  чекаючи запиту до CDN.

## Реліз

Одна команда на сайт. Реліз — це дві фази, бо між ними стоїть людський мердж:
тег мусить вказувати на коміт у `main` з перезібраним бандлом, саме його
jsDelivr роздає назавжди.

```bash
npm run pins                      # хто на якому тезі зараз (нічого не змінює)

npm run release:manera 1.0.1      # фаза 1: збірка -> перепін -> коміт -> PR
# ...мерджиш PR...
git checkout main && git pull
npm run release:manera            # фаза 2: ставить і пушить тег manera-v1.0.1
```

Далі — вставити `tilda_head_without_scripts/manera_head.html` у налаштування
сайту на Тільді (Site settings → More → HEAD code). До цього моменту для
відвідувачів не змінюється нічого.

Для robeauty так само: `npm run release:robeauty 1.0.7`.

Фаза 2 відмовиться працювати, якщо ти не на `main`, дерево брудне, `main`
розійшовся з `origin`, тег уже існує, або закомічений `dist/` не збігається зі
свіжою збіркою. Ці перевірки й є сенсом скрипта — вони роблять «затегав старий
бандл» неможливим станом.

**Теги незмінні.** jsDelivr кешує `@tag` назавжди, тому ніколи не переміщуй уже
випущений тег — завжди роби новий.

## Перевірити збірку, нічого не релізячи

```bash
npm run build:robeauty   # src/head.js        -> dist/head.min.js
npm run build:manera     # src/manera-head.js -> dist/manera.min.js
npm test                 # секція 5 Manera: що йде на сервер і в піксель після форми кошика
```
